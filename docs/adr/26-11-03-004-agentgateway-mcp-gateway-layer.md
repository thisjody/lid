# agentgateway is the build box's MCP front door: jobs reach ToolHive only through one gateway endpoint

**Status:** Accepted (pilot built and tested 2026-11-04)
**Date:** 2026-11-03
**Provenance:** Written at decision time.
**Concepts:** box, stack, composition, secrets

## Context
After 26-11-03-002 step 1, a job could use one ToolHive server at a time. Each server had its own proxy on `<host.internal_ip>`, and `disco_job.sh --tools <server>` pointed the job at one of them. The proxies have no caller authentication, so all a job could reach was decided by the host firewall and the box's egress allow. Step 2 planned to add caller checks by running a patched ToolHive build.

agentgateway (agentgateway/agentgateway, Apache-2.0, a static Rust binary) multiplexes several MCP servers behind one endpoint. It can authorize per tool with CEL rules and writes one access-log line per call. It can also act as an LLM gateway and as an egress proxy. We don't want either: the first would break the Claude token swap Discobox does for `api.anthropic.com`, and the second duplicates Discobox's egress control.

## Decision
**agentgateway v1.7.0 runs on the host as the only MCP endpoint a job can reach. ToolHive stays the cupboard that holds the keys and runs the servers.**
- **Pin and install.** Tag `v1.7.0`, commit `26f5aebe…`, release asset `agentgateway-linux-amd64` checked against its sha256 before install, in `stack/stack.yaml`. `stack_up.sh` installs it to `/usr/local/bin`. It is never installed by hand.
- **Endpoint.** `http://<host.internal_ip>:18800/mcp`. One multiplexed backend with targets `time` and `github`. Tool names are always `<target>_<tool>` (`prefixMode: always`). A failing target drops out and the others still serve (`failureMode: failOpen`), so an expired GitHub token doesn't take the time tools down with it.
- **ToolHive moves to loopback.** The proxies now listen on `127.0.0.1:18810` (time) and `:18811` (github). **Jobs reach ToolHive only through the gateway.** This is the "only via gateway" choice, and it is clean because the gateway runs as its own user (next point).
- **Its own user, a system unit.** The gateway runs as system user `epi-agw` under a hardened system unit `epistemic-agw.service`:
  - `ProtectSystem=strict` and `NoNewPrivileges`;
  - no capabilities, and a syscall filter;
  - admin and readiness on unix sockets in a 0750 runtime directory, with no TCP listener besides `:18800`.

  This departs from the "user unit like the thv units" style on purpose. Discobox's egress proxy and passt both run as uid 1000. If the gateway shared that uid, the firewall could not tell the gateway's connections to ToolHive apart from a sandbox's.
- **Host chain `EPI_STACK`, regenerated by `stack_up.sh`:**
  - `:18800` accepts only the host's own address;
  - uid 1000 may open no port on `<host.internal_ip>` except 18800, and may not open the ToolHive ports on loopback at all;
  - `epi-agw` may open only the ToolHive ports on loopback, and nothing else anywhere (no DNS, no internet).
- **No credential at the gateway.** The GitHub token stays in ToolHive's store and its one container. The gateway config holds no key and is root-owned and read-only to the service. agentgateway encrypts MCP session ids with a key: if none is set, it writes a generated one back into its config file. So `stack_up.sh` makes a random `SESSION_KEY` once, in `/etc/epistemic-stack/agw.env` (0600 root), and systemd passes it in.
- **Write tools refused twice.** github-mcp-server runs read-only. The gateway adds a CEL `mcpAuthorization` rule that allows only our two targets and no tool whose name reads as a write. A refused call returns JSON-RPC `-32602 "unknown resource"`, and the access log records `authorization denied`.
- **Jobs.** `disco_job.sh --tools gateway` gives the job one MCP server, `gateway`, at the endpoint above, with the box-level egress allow `<host.internal_ip>` (unchanged mechanism). `--tools time|github` are retired, since those proxies are no longer reachable from a sandbox.
- **Invariants.** `stack_test.sh` keeps (a)–(e), with (b) and (d) now going through the gateway, and adds:
  - (f) no direct route from the sandbox to ToolHive (host IP, loopback via the egress proxy, passt's host-loopback mapping), and the gateway is the only stack listener on the host IP;
  - (g) no GitHub credential in the gateway's config or environment; the config matches the repo; uid 1000 cannot read the gateway's environment;
  - (h) the gateway's user reaches ToolHive and nothing else;
  - (i) the github server can actually read GitHub.

  It also prints an INFO line showing what the multiplexed `initialize` carries.

## Consequences
- **One URL per job, with live tools from every server.** Proven by an end-to-end `disco_job.sh --tools gateway` run: Claude Code in a locked sandbox saw 31 `mcp__gateway__*` tools and called the time tool. It had no hosted-connector traffic, and the internet and the direct ToolHive ports were refused.
- **Step 2 of 26-11-03-002 can change shape.** Caller checks can be CEL rules at the gateway rather than a patched ToolHive build. That still needs a per-job identity the sandbox cannot leak (a Discobox secret routed to the host address is the candidate, not yet verified). That will be its own decision.
- **Another monthly-cadence pin**, a 96 MB binary, and a system user and system unit outside the user-unit pattern. `stack_check.sh` reports the pin against upstream and the unit's state.
- **Every job's context gets github's server instructions,** merged into the gateway's `initialize` That is expected: both targets are open to every job. Those instructions also describe write tools that read-only mode does not offer.
- **To hide a target from some callers, use a `condition` on the target, not an authorization rule.** Re-tested 2026-11-04 on v1.7.0: under a target `condition`, the hidden target is never initialized, and its name and instructions don't appear in `initialize`. A tool-level authorization rule (`mcp.tool.target`) hides the target's tools but not its instructions, because no tool exists at initialize. That was our first test's mistake, not an agentgateway bug. Calls to a hidden target fail with 500/-32603, and calls refused by an authorization rule fail with 400/-32602.
- **Found while testing, not caused by this change:** the github server cannot reach GitHub. Under rootless Podman 4.3, ToolHive's isolated network points the container's DNS at its own dnsmasq, which cannot resolve the egress proxy's container name (`lookup github-egress … no such host`). The earlier step-1 test only listed tools, so it never made a live call. Invariant (i) fails until this is fixed in the ToolHive layer. The fix is a separate decision, because it trades away part of that layer's egress isolation or needs a newer Podman. **Fixed 2026-11-04** with a newer Podman, isolation kept: 26-11-03-002, amendment of 2026-11-04. (i) now PASSES.
